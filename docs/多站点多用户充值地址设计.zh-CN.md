# 多站点、多用户充值地址设计

## 结论

可以用一个 MPC 根公钥和派生路径，为多个站点的用户生成确定性地址，例如路径包含站点槽位、用户槽位和地址序号。这样不必为每个充值用户单独运行一次 DKG。但要区分“路径能区分地址”和“路径能隔离风险”：同一个根 MPC key 派生出的所有地址仍共享同一密钥安全域。若达到门限的根分片泄露，攻击范围包括这个根密钥下的所有站点和用户。

BNB `tss-lib` v2.0.2 已提供非硬化子密钥派生和 ECDSA 签名 key derivation delta（KDD）接口；当前仓库尚未接入。当前 `internal/tssadapter` 的分布式签名仍调用 `signing.NewLocalParty`，没有使用 `NewLocalPartyWithKDD`，所以现阶段不能按路径签名这些子地址。

## 建议路径和映射

可以定义自己的、完全非硬化的路径结构，例如：

```text
m / app_namespace / chain_slot / site_slot / user_slot / address_index
```

所有索引必须是 `uint32` 且小于 `2^31`。不要把站点字符串直接当路径索引，也不要使用未经冲突处理的截断 hash。建议在注册表中为站点分配不可变的 `site_slot`，为站点内用户分配不可变的 `user_slot`；保存完整映射、分配时间、路径版本、根 `key_id`、epoch 和地址。用户删除后不重用旧槽位，防止地址被意外分给另一个主体。

每个 chain/网络定义唯一的 `chain_slot` 或使用不同的根 key。分配地址时，使用路径派生公钥生成相应链地址，并将 `site_id`、用户 ID、网络、path 和公钥地址写进数据库。EVM 和 TRON 都基于 secp256k1 公钥，可以根据同一个派生公钥分别编码成 EVM 和 TRON 地址；在产品上若要隔离链/网络的账务和策略，也可把链/网络纳入路径。

应把派生版本写入路径元数据，例如 `derivation_version`，同时存储规范化路径字符串和分配记录。不能只存一串地址而丢掉其根 key、路径、链和网络信息。

## BNB tss-lib 接口和前置条件

库中的 `crypto/ckd.DeriveChildKeyFromHierarchy` 返回路径的累计私钥 tweak `delta` 和扩展子公钥；`DeriveChildKey` 明确拒绝 `index >= 0x80000000`。`signing.NewLocalPartyWithKDD` 接收 tweak，`signing.UpdatePublicKeyAndAdjustBigXj` 用于调整公钥/验证用点。派生公式源自 BIP32 非硬化 CKD：父公钥和 chain code 可计算 tweak，从而得到子公钥。参考 [BNB tss-lib v2.0.2 child key derivation](https://github.com/bnb-chain/tss-lib/blob/v2.0.2/crypto/ckd/child_key_derivation.go)、[signing KDD API](https://github.com/bnb-chain/tss-lib/blob/v2.0.2/ecdsa/signing/local_party.go) 和 [BIP32 规范](https://github.com/bitcoin/bips/blob/master/bip-0032.mediawiki)。

有几个必须解决的工程条件：

- 派生还需要 32 字节 chain code。tss-lib 的常规 DKG 输出不是完整 BIP32 extended key，也没有自动为本项目产生可持久化的 chain code。项目需设计其安全生成、三方一致性确认、加密备份、版本管理和恢复流程；不能把 chain code 硬编码或随意由一个应用服务生成。
- BNB 这套实现只做非硬化派生。BIP44 常见路径的 purpose、coin type、account 段是 hardened，不能直接交给该接口。可重新定义仅使用非硬化索引的内部路径，或为每个安全隔离域独立做 DKG；不要以为能用 xpub 从 hardened 父节点继续派生。
- 所有签名参与方必须对相同的根 key、chain code、路径和派生版本算出相同 tweak/子公钥，并以子公钥验证结果。路径或 chain code 不匹配必须失败关闭。
- 派生 tweak 是公开可计算的偏移。如果多个子分片达到 tss 门限，攻击者也能用公开 tweak 将子秘密关系还原到父秘密关系。派生增加地址管理能力，不会把一个根密钥切成彼此独立的隔离域。

## 地址派生与入金的服务流程

1. DKG 建立并激活某个 `key_id`。将根公钥、委员会、chain code 的版本/承诺和派生方案登记为一个不可变 key manifest。
2. 业务服务通过受认证接口申请地址，提交站点、用户、链、网络和幂等 request ID。
3. 注册表校验站点和用户身份，原子分配从未用过的槽位，计算规范路径，并调用 MPC 公钥派生逻辑得出子公钥和地址。
4. 持久化 `site_id/user_id/chain/network/key_id/path_version/path/address/status` 唯一映射，再返回地址。重复请求应返回同一地址，不能分配另一个路径。
5. 充值监听服务按已登记的地址和网络扫描入账，处理重复日志、确认数、链重组和迟到交易，并将入账结果按站点和用户入账。地址派生组件本身不负责区块扫描或归集。
6. 归集或退款签名时，审批意图必须绑定根 `key_id`、路径版本/路径、站点、用户、链网络、接收方、金额、手续费、nonce/reference block 和原始交易摘要。签名节点必须自行验证这些字段及派生的子公钥，不能信任协调器传来的 digest 或地址标签。

由于每个站点拥有自己的用户与资产账本，建议至少在业务数据库层按 `(site_id, chain_id, network, user_id, address_index)` 建立唯一约束，并进行租户授权检查。若站点间法律/运营隔离要求强，直接给每站点配置独立 `key_id` / DKG 委员会及 KMS/审批域；共享一把根 key 会把所有站点变成共同的密码学风险域。

## 新增实现和测试清单

当前代码尚未实现上述地址服务。接入前建议分阶段完成：

- 在 DKG key record/manifest 中安全承载 chain code（或等价派生材料），并确保三方一致和可恢复。
- 为路径格式、索引范围、稳定槽位注册表、重复申请和数据库唯一性定义接口。
- 实现确定性公钥/地址派生；EVM 和 TRON 地址必须由同一子公钥正确编码，并进行链/网络区分。
- 将 KDD 接入分布式签名 runner；每方签名前独立核对路径和子公钥。不要原地篡改并持久化根 `LocalPartySaveData` 来代替每次会话 tweak。
- 将派生路径和站点/用户上下文绑定到不可变审批 intent，并限制允许的站点、路径范围、接收地址和额度。
- 进行端到端测试：路径派生可重现；非硬化边界有效、硬化索引被拒；不同站点/用户路径得到不同公钥；任意两方组合均能签出由对应子公钥验证的签名；错误路径/chain code/子公钥不能签名；根路径签名仍保持正确；重复地址申请幂等；跨站点映射不能越权；密钥更换后的旧地址余额和迟到入账处理正确。
- 在测试网压测充值扫描、重复事件、链重组、nonce/手续费竞争和批量归集，并做独立安全审查。

这些测试通过仍不能单独证明线上资金安全；上线前还需按[注意事项与未完成项](注意事项与未完成项.zh-CN.md)完成 signer 隔离、共享状态、恢复和监控工作。
