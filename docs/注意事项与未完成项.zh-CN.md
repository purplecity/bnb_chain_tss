# 注意事项与未完成项

这份文档把当前实现适用范围、关键安全边界和上线前还缺的工程工作集中列出，便于快速理解仓库状态。它不能代替代码审查、威胁建模或生产安全评估。

## 当前实现是什么

仓库已经实现了基于 BNB `tss-lib` v2.0.2 的三方 DKG、2-of-3 分布式签名基础流程，以及若干存储、传输、策略和链交易校验组件。签名服务是可嵌入 Go 程序的 HTTP handler；`cmd/tss-demo` 是单进程本地演示。仓库目前没有可直接部署的生产守护进程，也没有提供云资源创建和生产 RPC 服务。

生产前应重点阅读英文和中文的[使用指南](USAGE.zh-CN.md)、[架构说明](ARCHITECTURE.zh-CN.md)与[测试说明](TESTING.zh-CN.md)，并把以下缺项分配给具体实现和运维负责人。

## 密钥、分片和泄露处置

- 2-of-3 表示同一密钥代的任意两个分片可以签名。一个分片低于门限；两个分片已足以伪造该公钥的签名。
- resharing 会把同一公钥对应的门限份额迁移到新委员会，不会改变公钥，也不会让被复制的旧分片失效。它仅适用于旧密钥仍可信的计划迁移。
- 若怀疑门限份额或完整密钥已泄露，需新建密钥（全新 DKG）并将资产及合约/链上授权迁移到新公钥对应的地址。链上通常不能把已有账户地址的私钥“换掉”；新密钥意味着新地址。
- 单一根密钥的派生路径可以方便管理大量地址，但路径本身不是隔离边界。若某个站点需要独立的失陷范围，应为站点建立独立 MPC key/委员会/策略域，而不是只给同一根密钥换路径。
- 运行时内存不能承诺彻底擦除。磁盘加密、KMS envelope 和访问控制降低静态暴露风险，但无法阻止已被控制的运行中 signer 使用其分片参与签名。

## 当前仍属于部署方责任的部分

1. **Signer 部署与身份。** 当前提供 handler，不含可直接启动的生产 daemon、配置加载、证书轮换、进程监督和隔离部署模板。三个 signer 应使用独立账户、主机/区域、运维权限、网络和身份凭证。
2. **独立恢复路径。** 当前 DKG 记录由同一 signer 进程调用在线和恢复 wrapper。不同 KMS key reference 不等于真正的运营隔离。需要独立备份服务、恢复角色、IAM 边界、双人授权和恢复演练。
3. **生产持久化及协调。** FileStore 与 bbolt journal 是本地实现，没有云端共享存储、跨进程唯一请求注册表、分布式 fencing、部分激活修复和故障切换机制。云端应支持不可变版本/保留、审计和可验证恢复。
4. **激活证明。** 当前协调器提供 `ready_parties` 清单，signer 能核对其自身公钥及 manifest，但不能独立证明其他两个 signer 已完成备份。生产流程应验证每方签名的 READY 证明和备份回执，再签署激活 manifest。
5. **链上策略和状态。** `IntentValidator` 是注入接口。部署方仍需可信 EVM/TRON RPC、原子 EVM nonce 预留、TRON reference-block 验证、重组/reorg 处理、合约/代币白名单、手续费上限、额度/频率控制和审批系统集成。
6. **Resharing。** 当前 resharing helper 在进程内演示旧/新委员会状态转换，分布式多域协调、各阶段持久化/恢复、旧新身份重叠的安全设计和运维工作流尚未实现。不能把 helper 当成生产轮换工具。
7. **资产迁移。** 没有自动扫款或更新应用充值地址的服务。更换公钥后需要暂停/限制旧地址入金与支出，更新用户展示和监听映射，估算手续费，迁移资产，再持续监控旧地址的迟到入账。
8. **运行与响应。** 需有告警、审计留存、密钥/证书轮换、紧急冻结、节点离线处理、恢复演习、事故沟通和明确的资金迁移责任人。
9. **安全验证。** 当前测试覆盖大量单元和协议路径，但尚不覆盖多进程完整部署、真实云 KMS/IAM、故障注入、生产链状态竞争、长时间/负载测试、所有输入的 fuzz 和独立外部审计。

## 多站点充值地址的设计警示

使用 `site_id`、用户编号和地址序号组织派生路径是可行方向，细节见[多站点多用户充值地址设计](多站点多用户充值地址设计.zh-CN.md)。但当前签名流程仍调用 `signing.NewLocalParty`，尚未使用 tss-lib 的 `NewLocalPartyWithKDD`；仓库也没有地址分配注册表、站点/用户映射、充值扫描和归集服务。因此不能只配置一个路径就认为充值地址能力已经存在。

实现之前至少要决定：站点是否共享一个根密钥、站点 ID 如何稳定映射到整数索引、chain code 如何生成/备份/版本化、如何阻止路径冲突、路径和用户身份如何进入审批策略，以及用户地址如何在更换根密钥后迁移。BNB 库的该派生实现只支持非硬化索引；也不要把 BIP32 标准路径中的 hardened 分层直接视为可用。

## 启用真实资金前的门槛

需先完成架构/代码审查和独立密码学审查，完成生产 signer 与恢复域隔离、共享存储与请求 fencing、独立 READY/备份证明、链上 validator 和 nonce 控制，补齐多进程/崩溃/恢复测试，并在测试网演练从 DKG 到签名、广播、确认、resharing、新地址迁移和事故响应的全过程。现阶段此仓库应作为研发基础，而非直接托管真实资产的系统。
